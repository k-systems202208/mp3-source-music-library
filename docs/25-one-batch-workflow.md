# ワンバッチ開発運用

対象: 自宅音楽ライブラリの通常の開発・保守変更
目的: ユーザーが複数のGitコマンドを手作業で順番に実行する運用をやめ、原則として1本のバッチ実行で安全に変更を反映する。

## 1. 基本方針

通常の変更作業では、ChatGPT/Codex等の支援ツールはユーザーに多数のコマンドを個別入力させない。

ユーザー操作は原則として次の1回にまとめる。

```text
apply-<topic>.bat
```

バッチ内部で、事前確認、ブランチ作成、変更適用、試験、コミット、Push、Pull Request作成、マージ、`main`への復帰、作業ブランチ削除までを順番に実行する。

ただし、安全性を優先し、異常時はその場で停止する。失敗を無視して後続処理へ進んではならない。

## 2. 対象範囲

ワンバッチ方式の主な対象は次のとおり。

- 現行ソースの修正
- テストの追加・修正
- 文書の追加・修正
- 小規模な保守作業
- 機能追加の通常開発フロー
- Pull Requestを経由した`main`への反映

正式リリースでは、通常の回帰確認に加えて`windows-installer/00_build_installer.bat`による正式ビルド確認を行う。

## 3. 標準処理順序

1本のバッチは、原則として次の順序で処理する。

### 3.1 事前確認

- Gitリポジトリ内で実行されていることを確認する。
- `git status`で未コミット変更がないことを確認する。
- 現在の変更を勝手に破棄しない。
- GitHub CLIを利用する場合は`gh`が利用可能であることを確認する。
- 必要に応じてGitHub認証状態を確認する。

未コミット変更がある場合は停止し、既存作業を保護する。

### 3.2 `main`の最新化

- `main`へ切り替える。
- `git pull --ff-only origin main`で最新化する。
- fast-forwardできない場合は停止する。

自動でrebase、force、`reset --hard`を行わない。

### 3.3 作業ブランチ作成

変更内容ごとに専用ブランチを作成する。

例:

```text
feature/<topic>
fix/<topic>
docs/<topic>
maintenance/<topic>
```

現行開発で`main`へ直接コミットしない。

### 3.4 変更適用

バッチに含めた処理で必要なファイルだけを変更する。

現行製品ソースの正本は`windows-installer/src/`であり、リポジトリ直下の旧ソースを誤って更新しない。詳細は`AGENTS.md`と`LEGACY_SOURCE_NOTICE.md`を参照する。

### 3.5 差分検証

最低限、次を確認する。

- 想定ファイルだけが変更されている。
- `git diff --check`が成功する。
- 意図しない一時ファイルや生成物が含まれていない。
- 既存ファイルを丸ごと書き換えて不要な改行差分を発生させていない。

ステージングには原則として`git add .`を使わず、対象パスを明示する。

### 3.6 試験

変更内容に応じた関連テストを実行する。

必須テストの選択は `windows-installer/docs/TEST_MATRIX_v2.7.7.md` に従う。

通常の機能変更では、関連テストに加えて次を実行する。

```text
windows-installer\06_verify_next_improvements.bat
```

テストが1件でも失敗した場合は、Commit、Push、PR作成、Mergeへ進まない。

文書だけの変更など、実行コードへ影響しない変更では、必要性を判断して試験範囲を縮小できる。ただし`git diff --check`は行う。

### 3.7 CommitとPush

- 対象ファイルだけをステージする。
- `git diff --cached --check`を実行する。
- 変更内容が分かるCommitメッセージを付ける。
- 作業ブランチを`origin`へPushする。

### 3.8 Pull Request

GitHub CLIが利用可能な場合は、バッチからDraft Pull Requestを作成する。

PR本文には最低限、次を含める。

- 変更概要
- 変更理由
- 実施した試験
- 試験結果
- 対象Commitまたは主要変更点

PRのbaseは`main`、headは作業ブランチとする。

### 3.9 Merge確認

Mergeは取り消しにくい操作のため、バッチ内でユーザーの明示確認を取る。

例:

```text
このPull Requestをmainへマージしますか? YES / NO
```

`YES`以外ではMergeしない。

通常は意味のあるCommit履歴を残すため`merge`方式を使用する。意図的に履歴を1Commitへまとめたい場合だけ`squash`を選ぶ。

### 3.10 後処理

Merge成功後は次を自動化する。

- `main`へ切り替える。
- `origin/main`をfast-forwardで取得する。
- ローカル作業ブランチを削除する。
- リモート作業ブランチを削除する。
- `git status -sb`で最終状態を表示する。

最終的に次の状態を目標とする。

```text
## main...origin/main
```

## 4. 安全ルール

ワンバッチ化は「何でも自動実行する」ことではない。次の安全ルールを優先する。

- 未コミット変更を自動削除しない。
- `git reset --hard`を自動実行しない。
- force pushしない。
- `main`へ直接Commitしない。
- テスト失敗後にCommit・Push・Mergeしない。
- 想定外の差分を自動でステージしない。
- 競合を自動解決しない。
- Merge前にユーザー確認を取る。
- エラー時は処理を停止し、どの段階で止まったか表示する。

## 5. 異常終了時の扱い

途中で失敗した場合、バッチは可能な限り既存状態を保持して停止する。

自動で「元に戻す」処理を行うと、ユーザーの既存作業を消す危険があるため、原則として強制ロールバックはしない。

停止時には少なくとも次を表示する。

- 失敗した処理
- 現在のブランチ
- `git status --short`
- PRを作成済みかどうか
- 次に必要な対応

## 6. 支援ツール側の運用ルール

ChatGPT/Codex等が変更手順を提示する場合は、原則として次の運用とする。

- 数個以上のGitコマンドをユーザーへ順番に入力させる方式を避ける。
- 変更内容と検証処理をまとめた自己完結型の`.bat`を優先して作成する。
- Windows PowerShell 5.1の文字コード問題を避ける必要がある場合は、ASCIIのバッチからUTF-8スクリプトを生成する等の安全な方式を使う。
- バッチは再実行時の状態を考慮し、既存ブランチや既存PRを誤って上書きしない。
- ユーザーが確認すべき内容は、バッチ内の明確な確認プロンプトへ集約する。
- 手動コマンドが必要になるのは、競合、認証・権限制約、仕様判断、試験失敗など、自動継続すべきでない場合に限定する。

## 7. 今後の標準

今後、このリポジトリでChatGPTと共同して通常の変更を行う場合は、特別な理由がない限りワンバッチ方式を標準とする。

個別コマンドを多数実行する方式へ戻す必要がある場合は、その理由を明示する。
