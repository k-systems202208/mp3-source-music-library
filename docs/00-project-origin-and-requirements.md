# プロジェクトの起点と初期要件

## 起点

最初の目的は、iTunesからエクスポートしたXMLに含まれる8,383曲を、追加費用なしで素早く検索することでした。初期版はXMLをJSONへ変換し、単一HTMLへ埋め込み、ブラウザだけで検索する静的アプリでした。

## 初期要件

- 曲名、アーティスト、アルバム、作曲者を検索できる
- 大量データでも操作が止まりにくい
- 図書館のカード目録を連想する読みやすいUI
- 曲、アーティスト、アルバムを行き来できる
- 表記補正は自動で決めつけず、利用者が確認して保存できる
- 外部の有料サービスを可能な限り使わない
- 市販音源や個人情報を公開しない

## 発展の理由

### 静的HTMLから外部JSONへ

データとUIを分離し、更新作業とファイルサイズを扱いやすくしました。

### JSONからMP3正本へ

JSONと実ファイルの照合ずれを避けるため、音源の存在はMP3フォルダを正本としました。

### SQLiteへ

再生回数、表記補正、追加日、スキャン履歴など、MP3タグへ直接書き戻したくない管理情報を保存するためSQLiteを採用しました。大量曲を一度にブラウザへ送らず、APIからページ単位で取得できる構成へ移行しました。

### Windows管理画面とインストーラーへ

Pythonやバッチファイルを意識せず、音楽フォルダ選択、起動、停止、外部接続設定を行えるようにしました。

### LAN・Tailscaleへ

同一Wi-Fiの端末と外出先の端末から利用できるようにしました。公開インターネットへ直接ポートを開けず、Tailscale Serveを使用します。

### v2.7.0の利用者別状態へ

家族が同じライブラリを利用すると、共有の再生回数やお気に入りでは「誰が聴いたか」「誰のお気に入りか」を区別できません。このため、次を新要件として追加しました。

- 自宅PCの管理者をオーナーとして識別する
- Tailscale利用者をログイン単位で識別する
- 再生回数、最終再生日時、お気に入りを利用者ごとに保存する
- 匿名接続では誤った利用者へ状態を保存しない
- 家族のTailscaleアカウントを自動でオーナーにしない
- ローカルオーナーと本人のTailscaleアカウントは、明示確認後に関連付ける
- 関連付け前に既存の個人状態を安全に統合する
- 旧版の共通状態を失わずオーナーへ移行する

## 現在も維持する設計原則

1. MP3音源を勝手に変更・移動しない
2. 管理情報はSQLiteへ保存する
3. 自動推測より誤結合防止を優先する
4. 破壊的変更の前にバックアップを作成する
5. 外部公開範囲を最小化する
6. 失敗時は中途半端な状態を残さない
7. UIの便利さより、正本と識別境界を明確にする
